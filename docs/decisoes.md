## Tomadas

| ID | Decisão | Fundamento |
|---|---|---|
| D-04 | `applicationId`/namespace `ao.kupila.gestaonegocios`; nome visível **Kupila-Gestão de negócios** | Não existe app Android anterior do Kupila a preservar; separado de `ao.spotec.pdvdigital` |
| D-09 | Convenção de aluguer unificada: dia=1, semana=7, quinzena=15, mês=30, ano=360 dias comerciais. Base mínima B = preço × ceil(dias_mín/dias_unidade). Equivalente mensal = preço × 30/dias_unidade (dia ×30, semana ×30/7, quinzena ×2, ano ÷12). Unidade personalizada exige equivalência mensal explícita; sem ela a operação fica bloqueada para revisão | Reproduz exactamente os dois cálculos da origem (12448-12464 e 16707), que já são coerentes com mês de 30 dias, e elimina o caso `OTHER = mês` (incons. B) |
| D-10 | Dinheiro em `BigDecimal` (AOA, escala 2), percentagens em `BigDecimal`; cálculo interno escala 10; arredondamento HALF_UP apenas ao fixar cada montante (D, C, T, promoções); N, R e Q derivados por subtracção/soma de montantes já fixados | Conservação exacta: D = C + N; B = D + R |
| D-11 | Aluguer: C = B × c/100; validações D>0, D≤B, 0≤C≤D; inválido bloqueia a operação e encaminha ao Administrador (sem `max(0,…)`) | Secção 17 e caso de teste c=40% |
| D-12 | Simulador usa o mesmo motor; no aluguer usa meses de sinal (não percentagem) | Incons. B; secção 32 |
| D-13 | Custódia até decisão da vistoria; OTP válido cria decisão + pedido de liberação, nunca "pago" | Incons. A/C |
| D-14 | Dados de demonstração KPL-001/002/003 não existem no build de produção | 1.0.231 (31378) |
| D-15 | Navegação "avançar" do HTML não é reproduzida; Voltar do Android com predictive back preserva contexto | Adaptação de navegador |
| D-16 | OCR on-device com ML Kit (substitui Tesseract.js); OCR só prepara evidência | Stack PDV comprovada |
| D-17 | Código das Functions em `backend/functions` (Node 22, firebase-functions v2), regras em `backend/firestore.rules` e `backend/storage.rules`, testado no Firebase Emulator | Coerente com `functions/` do PDV (Node 22) |
| D-18 | Base Room separada por conta (`kupila-<uidHash>.db`) | Isolamento entre contas (secção 9) |
| D-20 | Firestore mantém os nomes de campos da origem (`status`, `ownerId`, `userId`, …); o domínio Kotlin usa nomes portugueses e os DTOs fazem o mapeamento | Evita migrar dados reais só por designação (secções 0 e 35) |
| D-21 | Papel efectivo por custom claims (`papel`, `estado`) definidos só pelo Central; o campo `role` do perfil é informativo | "Não conceder privilégios porque uma função se chamava isManager" (secção 26) |
| D-22 | Projecção pública exclui `doc`, `otp`, `ownerSnapshot`, bairro, ponto de referência e recebimento (a origem deixava `doc` e `otp` no documento público, 12265-12271 e 14923) | Incons. F |
| D-23 | IBAN validado no formato angolano (AO + 23 dígitos); a origem só exigia campo não vazio | Evita liberações falhadas |
| D-24 | Coil 3.3.0 (coil-compose + coil-network-okhttp) para imagens remotas | O PDV não apresenta imagens remotas; galerias/miniaturas do marketplace exigem cache, redimensionamento e cancelamento (secções 6 e 10). OkHttp 5.5.0 já é a versão herdada |
| D-25 | Inactividade: aviso nos últimos 20% do tempo (entre 15 e 60 s) e, ao esgotar, logout com a mensagem da origem; cálculo pelo tempo decorrido (`elapsedRealtime`) e revalidado ao voltar ao 1.º plano | `getSessionWarningMs`/`automaticSessionLock` (10736-10790) |
| D-27 | **Modo Spark (vigente)**: sem Cloud Functions. Autoridade = regras Firestore/Storage (papel e estado lidos de `users/{uid}`, nunca de campo editável pelo próprio; OTP verificado nas regras com `hashing.sha256` contra um segredo ilegível; versões e transições de estado validadas nas regras) + transacções do app + **processamento pelo Administrador no próprio app** para o que exige decisão (confirmar comprovativos/pagamentos, liberações, reembolsos). **Modo Blaze (futuro)**: as mesmas operações pelas Callable Functions de `backend/functions` (já escritas e testadas). Selecção por `BuildConfig.MODO` = `spark`/`api`, como no PDV Digital (`CentralSpark`/`CentralApi`) | Decisão do utilizador (2026-10-23). Limitações do Spark registadas: sem revogação de refresh tokens nem desactivação Auth pelo servidor (o estado da conta é imposto pelas regras e pelo app); sem provedor de pagamentos automático (confirmação manual auditada pelo Administrador); sem tarefas agendadas (expiração aplicada na leitura e pelo app do Administrador) |
| D-28 | Repositório público `BentoNever/kupila` (nome e visibilidade decididos pelo utilizador). Publicação feita pela API do GitHub (não há `git` instalado). Configuração Firebase e chaves nunca entram no repositório | Decisão do utilizador (2026-10-23) |
| D-29 | **Ligação ao Firebase real em modo compatível com a app HTML em uso** (pedido do utilizador, 2026-10-23): (1) as regras de produção (Kupila 1.0.188, publicadas a 2026-09-02, cópia em `backend/producao-actual/`) **não são alteradas** — o Android escreve com o mesmo esquema, colecções, nomes de campos e datas ISO do HTML, para não perder cadastros, logins e dados; (2) imagens inline (~64 KB) e comprovativos em partes em `productFiles`, como o HTML (sem regras de Storage publicadas); (3) a sessão exclusiva usa o mesmo documento `activeSessions/{uid}` (`deviceId`, datas ISO), funcionando entre web e Android; (4) **confirmação de pagamentos pelo Administrador no app** (o HTML aguardava um backend inexistente; as regras já reservam esse papel ao "backend/Admin"); (5) reservas confirmadas no Android guardam o OTP como hash PBKDF2 com sal (o código em claro só vai para o comprovativo do Cliente, em `paymentSubmissions`, legível apenas por ele) — reservas antigas com `otp` em claro continuam válidas; (6) notificações derivadas dos eventos que o utilizador já pode ler. Apps Android registadas no projecto: `ao.kupila.gestaonegocios` e `.dev` | Riscos herdados das regras actuais (participantes podem escrever campos que deviam ser só do servidor) ficam registados em `docs/riscos-regras-producao.md`, com uma proposta de endurecimento a publicar em conjunto com uma actualização do HTML ou com o plano Blaze |
| D-26 | Emulador Firebase como ambiente de desenvolvimento/teste; no Windows o processo do Firestore pode ficar órfão — `tools/central-testes.ps1` liberta as portas | Execução reprodutível dos testes do Central |
